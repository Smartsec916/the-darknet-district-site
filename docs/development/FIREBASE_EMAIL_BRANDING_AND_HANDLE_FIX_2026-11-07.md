# Firebase email branding and District handle fix — 2026-11-07

## What was found

The site's `firebase-auth.js` uses Firebase project `the-darknet-district-71873`, whose web config has numeric sender/project number `166866456762`. `district-identity.js` calls `sendSignInLinkToEmail()` with a return URL and no email display-name option. The reported `project-166866456762` in the second-account sign-in email is therefore a Firebase project/template branding issue, not a handle or game-code setting. The exact email headers and current Firebase Console template values were not available here. One Gmail spam placement does not establish its cause.

The Python handle registry previously removed trailing digits before checking protected names. That made both `Iris_02` and `IriS02` compare as `Iris`. The revised rule keeps exact NPC names and `Iris_Bot`/`TheIris` style impersonation protected, allows numbered character-inspired handles, and continues to protect numbered staff/site roles such as `admin_02`. Formatting remains 3–20 ASCII letters, digits or underscores. The Firestore reservation key remains the lowercase handle; the transaction still rejects another UID's reservation with HTTP 409. Existing handle records and saves are not migrated or modified.

## Manual Firebase Console branding steps (owner only; no production change made)

1. In Firebase Console, select **the-darknet-district-71873**. Under **Project settings → General**, inspect **Public-facing name** and set it to **The Darknet District** if it still says `project-166866456762`. Check the support email displayed there. Keep the project ID, project number, providers, and credentials unchanged.
2. Under **Authentication → Templates → Email link (sign-in)**, inspect the sender display name, subject, reply-to address, and body. Where editable, use **The Darknet District** as the sender display name and a clear sign-in subject. Save only after previewing the template and confirming the action link still returns to `thedarknetdistrict.com`. Console labels can differ by Firebase UI version; the public-facing name may supply the sender name when the template does not expose a separate field.
3. Optional later: in **Authentication → Templates → Customize domain** (if offered for this project), review a verified domain or subdomain owned by the District for authentication emails/action links. This requires DNS ownership verification and possibly sender-domain SPF/DKIM/DMARC records. A custom sender domain and a custom action-link domain are separate settings; do not assume either follows from changing the display name. Do not alter `authDomain`, authorized domains, DNS, or `ActionCodeSettings` until a specific domain is selected and an end-to-end link test is planned. No custom domain is needed to fix the displayed project name.
4. Send a fresh link to an existing dedicated test account. In Gmail use **Show original** to inspect the visible From name/address, Return-Path, Authentication-Results (SPF, DKIM, DMARC), and link host. Compare with the expected Firebase domain or any configured custom domain; do not forward the live sign-in link or headers containing a usable token. If Gmail still marks it spam, use **Report not spam** for that test message and compare a second recipient. Possible causes include an unbranded sender, new sender reputation, domain/authentication alignment, or message/link content; none is proven without the headers. Firebase Console's template preview and Gmail's original-message results are the evidence needed before changing DNS or code.

The multiplayer hub still requires a registered account plus API-verified handle and character on every join; it never accepts a browser-supplied name. These are local code/test results; production Firebase and a live two-account session remain unverified.
