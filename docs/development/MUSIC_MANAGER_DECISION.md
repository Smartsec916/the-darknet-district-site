# Shared Sleeping Pod music and administrator publishing

The public catalog is `void-runner/music-catalog.js`. The website Sleeping Pod and the 3D Sleeping Pod read its published entries in the same order and stream the same files from `attached_assets/`. The 27 existing MP3 files remain where they are; no audio was copied. The website keeps its current shuffled playback. The game offers the same hosted playlist by default, as David requested. **My music** remains local to the player's browser. The 2025 Riffusion rights question remains open.

GitHub Pages is a static host and cannot receive authenticated browser uploads. The existing game API uses Firebase identity and a configured developer allowlist, but has no managed media store or GitHub publishing credential. A client-only Music Manager would allow unauthorized writes if it had any publishing capability, so no upload or edit controls are enabled yet.

The lowest-cost publishing route is a small authenticated endpoint on the existing Render game API. It would verify the Firebase token and developer identity on every operation, then validate MP3/other supported audio by signature and size, sanitize title/artist/description, reject duplicate content hashes and duplicate URLs, and submit a repository PR containing the media file and catalog edit. A narrowly scoped GitHub App or fine-grained credential would be needed on Render; it must never appear in the static site. The owner would review that PR and merge it to publish through the existing Pages workflow. Removing a catalog entry would leave its media file untouched. Preview would use a browser-local object URL for an upload or the registered URL, without publishing it. External URLs would need HTTPS, an approved host list, and server-side checks against private addresses and redirects before publication.

An alternative is Firebase Storage plus Firestore metadata, both already represented in backend dependencies. It still needs a storage bucket, rules, billing and production configuration, and would make the catalog dynamic. That is more infrastructure for this milestone, so the repository PR route is preferred pending the owner's approval of credentials and upload limits. Until that decision, new tracks can be added by a reviewed repository change to the catalog and `attached_assets/`; both players will then see the same published track after Pages deploys.
