# Conversation and character development milestone

Branch: `codex/conversations-character-foundation`, based on `codex/social-foundation` at `dbab0e5`.

Walking NPC conversations, including VR companion calls through `talk()`, now use a floating screen-space panel. Opening the panel leaves `mode='walking'`; WASD and camera remain available. The panel can be minimized and restored, and its previous NPC lines are saved locally by authenticated UID or guest scope. The Social tab filters local NPC history by all, recent, unread, and character. These records are browser-local story text, never player-to-player messages. Player messaging, cross-device history, privacy, blocking, reporting, and notifications require an authenticated social service.

The common `talk()` path is converted. Archived Vesper tutorial code still has two direct `panel()` dialogue branches; the District mission pool makes that tutorial unreachable in current campaigns, but those branches need conversion before archived missions can return. A full VR companion playthrough and long-distance conversation check remain outstanding.

The first character endpoint uses the existing `vr_players` document and a transaction to create at most one character per authenticated account. Anonymous Firebase accounts cannot create a permanent character. The current choice is one of two existing District crowd looks: `district-resident` (female) or `district-smuggler` (male). Only a server-allowlisted administrator can reserve the existing `admin` look, in the same single slot. The endpoint does not change campaign saves or require a migration. The UI presents only supported model choices; the first-person player is not yet represented by that model in the 3D world.

The selected GLBs have existing idle, talk, and walk clips on the game's Mixamo rig. Their clothing and hairstyles are baked into each model. Mesh swap, independent hair and clothing colors, shared skeleton identity, and network animation compatibility have **not** been verified; those controls are deliberately absent. Named NPCs and VR companion assets, animations, movement, and environment are unchanged. The Tesana ZIP characters remain unimported: they have no compatible clips and their shared-library rights remain unverified. See `TESANA_ASSET_AUDIT.md`.

Achievements now use merchandise, district, arcade, and community categories in catalog previews. A display helper filters public, verified unlock records and puts merchandise first. It grants nothing and does not accept purchase details. The Achievement Manager remains a read-only administrator preview. A server event ledger, icon storage, definition editing, featured selections, player progress, grants and revocations, and purchase verification are still required.

The playable Admin/Iris handoff is **not implemented**. The game has no authoritative social-area presence, session lease, shared avatar state, or two-client synchronization. A safe handoff needs a server-owned single Admin lease with expiry and disconnect recovery, atomic NPC/Iris responsibility state, and room broadcasts before the NPC can disappear for other players. It must not key authority off a display name or client appearance. Current Admin and Iris dialogue and missions remain in the archive; District campaigns keep the old mission pool closed.

The next gate is a two-client social-room prototype using existing Firebase authentication and an economical backend design, with bounded position/animation updates and server-verified session identity. It needs tests for lease expiry, duplicate Admin prevention, disconnect restoration, Iris mission references, message permissions, and mobile access to the same social API. No production database or service is changed by this branch.

Validation on 2026-11-05: Node suite 609 passed, 1 skipped; 36 API/save tests passed in the workspace Python environment; local Chromium low and high conversation checks passed movement, camera, minimize/restore, Social history/filtering, and no page errors; device-gate browser checks passed 9/9. These browser runs use software GL and emulated phones. No physical GPU, ROG Ally, real account/API session, long-distance conversation, or two-client multiplayer test was performed.
