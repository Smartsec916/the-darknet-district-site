# District social and achievement foundation

This branch starts returning local campaigns in pod 01 and closes the old mission pool without deleting mission definitions or saved mission records. Credits, equipment, ships, and progression remain in the save. The previous saved location is recorded in `story.flags.previousLocation` when a player arrives from elsewhere. The local campaign is not overwritten until the player exits the pod or otherwise saves. This is a single-player entry flow; it is not a multiplayer pod allocator.

The Personal HUD's Social section now presents the local pilot and known NPCs with one profile card style. Profile keys are namespaced (`player:` versus `npc:`), so an NPC cannot become a player identity. Existing story-derived messages appear in a scrollable conversation style; they are still local story data, not player messages. The existing spoken dialogue window uses the same bubble styling. Actual player messages, friends, discovery, blocking, reports, and cross-device history need an authenticated social backend. Do not treat a visible profile or local guest handle as verified identity.

`void-runner/achievements.js` defines example achievements with reusable event rules and a read-only progress preview. The player profile and server-authorized Developer Tools show catalog previews only. No client unlock, purchase verification, score submission, reward, or grant endpoint exists. A production manager needs server-side administrator authorization on every edit, versioned definitions, icon validation/storage, a grant/revoke audit log, and an event ledger with idempotency keys. Only trusted purchase webhooks, arcade score verification, or game-server events may unlock achievements. A browser flag marked `verified` is insufficient authority.

For multiplayer, reuse Firebase identity and the existing developer allowlist, then add a social session service for location-scoped presence and avatar state. The client sends bounded position/animation updates to a server that validates identity, rate, area, and movement. Broadcast only within social rooms. Persist profiles, friends, blocks, reports, and messages through server-authorized APIs; guests use isolated ephemeral identities. Text chat requires rate limits, blocking, reporting, privacy settings, and moderation before it opens publicly. Phones consume the same social API through a lightweight page and never load the 3D client. Spaceflight, combat, and missions stay local single-player systems. No new paid service or production schema is authorized here. The first multiplayer claim requires two separately authenticated clients to enter one room and see each other's avatar movement and a permitted message.

Next: verify the returning-account pod flow against the real API; replace the remaining traditional dialogue layout with a complete threaded interface and safe scripted choices; build the server-authorized social and achievement endpoints; then run two-client and physical-device tests. The Tesana pod 01 art is a first adaptation; a fuller geometry and lighting pass remains, while protected areas are unchanged.
