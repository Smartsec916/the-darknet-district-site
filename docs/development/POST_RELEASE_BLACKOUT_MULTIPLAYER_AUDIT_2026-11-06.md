## B. Firebase and leaderboard security

The v2 API uses project `the-darknet-district-71873`, Firebase Admin application-default credentials, server verification of ID tokens with revocation checking, and the District-wide handle registry. `bp_tesana_stats`, `bp_tesana_leaderboard`, `bp_tesana_runs`, and `bp_tesana_events` are separate from legacy score collections. Run IDs and player IDs are server-generated; the UID comes from the verified token. Runs enforce a handle, a start cooldown, ordered sectors, time bounds, bounded event counts, a recalculated Tesana score, boss events on boss sectors, and transactional duplicate checks. API tests cover cross-UID rejection, old-score separation, all 12 sector submissions, and the new board. A browser can still fabricate plausible events/timing; this is constrained evidence, **not server-authoritative proof of actual gameplay**. Do not treat this board as anti-cheat secure for prizes or merchandise.

`blackout-protocol/firestore.rules` is a **fragment** denying direct client access to the four v2 collections. It is not proof of active production rules; another broader matching allow rule could override it. Firebase Admin bypasses client rules, so deny-all browser rules are compatible with the API. v2 uses direct document lookups, a single-field `bestScore` order/filter/count, and a Top 100 query; no custom composite index is declared in the repository. Confirm the actual project/index response rather than creating an index blindly.

**Owner/operator read-only checks before a backend deploy:** in Firebase Console select `the-darknet-district-71873`; inspect the *complete active* Firestore rules and use the simulator for anonymous and ordinary authenticated access to dummy documents in each `bp_tesana_*` collection (both reads and writes must fail). Inspect Auth authorized domains and test a dedicated account's real token against `/api/identity/me` and its public handle. In the Render Python service, confirm Firebase Admin credentials work for that same project without showing key material, and that at least one of `DISTRICT_HANDLES_ENABLED`, `VOID_ACCOUNTS_ENABLED`, or `BLACKOUT_ACCOUNTS_ENABLED` is `true` for the identity/handle API. `BLACKOUT_ACCOUNTS_ENABLED` gates the *legacy* Blackout routes; v2 routes call `services(require_legacy_flag=False)` but still need Admin credentials and a handle. Do not change Firestore rules, flags, or credentials as part of this audit.
