## Rollback

Normal rollback: choose an immutable published generation or repository baseline in the editor, preview and acknowledge it, enter the reason and submit against the current generation. It creates a new immutable version/audit and atomically updates the active pointer. Prior versions and player saves remain unchanged. Running pages remain pinned; reload adopts the rollback. Other backend workers may serve the preceding complete version for up to five seconds due to the bounded public-read cache.

For a source-build mismatch or exhausted publication retention, turn VOID_CONTENT_SERVING_ENABLED off to return new requests to baseline; an online client receiving disabled clears only its published-content cache. An offline or already-running page cannot be remotely rewritten and stays on its compatible pinned snapshot until reload/reconnect. Do not delete player saves, private drafts or audit history to roll back.

If code itself needs rollback, revert its reviewed merge on the appropriate branch and deploy the previous matching client/backend builds through the existing process. Verify service-worker version, disabled feature flags, publication endpoint and normal save/auth behaviour. This PR has no new save IDs, reward migration, production reset or schema migration to undo.

## Cost and retention checks

Public serving is off by default (zero reads from that endpoint). Enabled public traffic incurs at most one active-document read per five-second window per backend worker while requests arrive; the cache has no polling timer. Publication normally reads candidate/history and writes four documents. Histories stop at 100 operations pending an explicitly reviewed retention policy; no automatic production deletion is implemented. Maximum snapshot payload is 256KiB and the browser retains one published cache slot. Existing shared quotas, worker counts, traffic and index overhead determine actual cost; zero additional charges are not certified here.
